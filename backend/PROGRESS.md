## Structural change — monorepo layout & deployment

The project became a monorepo and the whole stack is started from the **repository root**:

```
.
├── frontend/          # React + Vite (was the repository root)
├── backend/           # FastAPI (unchanged)
├── docker-compose.yml # db + api + frontend  (moved from backend/)
├── docker-compose.override.example.yml
└── .env.example       # the configuration of the whole stack
```

The deployment follows the pattern of the reference project: **three containers on one compose
network, no reverse proxy in the repository** (the nginx configuration belongs to the server).

| Service | Image | In the network | Published on the host |
| --- | --- | --- | --- |
| `db` | postgres:16-alpine | `db:5432` | `127.0.0.1:5433` (host only) |
| `api` | `./backend` | `api:8000` | `127.0.0.1:8080` (host only) |
| `frontend` | `./frontend` (vite dev server) | `frontend:8081` | `0.0.0.0:8081` |

What changed:

- The compose file lives in the root and builds **three** services. The api has a health check (a
  Python one-liner, the slim image has no curl) and the frontend depends on it.
- The frontend container runs the **vite dev server** on port 8081 (the container's
  `EXPOSE 8081`) and proxies `/api` to `http://api:8000` (`API_PROXY_TARGET`, resolved by Docker
  DNS inside the network). The browser only ever calls the relative `/api` path, so the app and
  the API share one origin and no CORS is needed — the nginx configuration of the server stays
  outside the repository.
- The source folder is mounted into the frontend container (hot reload) and a named volume keeps the
  image's Linux `node_modules` from being shadowed by the Windows one.
- The db and the api are bound to `127.0.0.1` — they are **not** reachable from outside the
  machine. Only the frontend is published.
- `docker-compose.override.example.yml` documents how to move a mapping when Windows reserves the
  port (the `!override` trick replaces the ports list instead of appending to it).
- **One `.env` in the repository root** configures the stack (docker compose, the backend and the
  vite dev server). `backend/.env` overrides single values for a local run and wins: the settings
  read `env_file=(<root>/.env, <backend>/.env)` and pydantic-settings applies the files in order
  (the last one wins). The vite config uses `envDir: '..'` and reads the proxy target from
  `process.env` (the container) or from the `.env` (the host).
- `@types/node` was added to the frontend so the vite config can read `process.env`.
- `.dockerignore` for both build contexts (the `.venv` and `node_modules` stay out of the build).

## Decisions

- `CORS_ORIGINS` is parsed as a comma separated list (`Annotated[list[str], NoDecode]` +
  `field_validator`), because pydantic-settings would otherwise try to JSON-decode the value.
- The health endpoint lives in its own `health_router` inside `app/api/v1/public.py` so it can be
  mounted both at the root and under `/api/v1` without duplicating the other public routes.
- `Settings.validate_or_raise()` is called inside `create_app()`, so a misconfigured production
  environment prevents the process from starting (not just the first request).
- Validation errors are translated to Persian via a small mapping of Pydantic error types; unknown
  error types fall back to a generic Persian message so no English leaks to end users.
- `tzdata` is added to runtime requirements because Windows Python has no bundled IANA timezone database.
- Local development uses a Python 3.12 virtualenv in `backend/.venv` (the machine default is 3.13,
  the project targets 3.12).
- `CURRENT_TIMESTAMP` is used as the portable server side `now()`: it is valid in PostgreSQL
  (same as `now()`, returns `timestamptz`) and in SQLite (returns UTC text). `UTCDateTime`
  normalises the values so both backends return timezone aware UTC datetimes.
- `shop_settings.id` is declared with `autoincrement=False` so PostgreSQL does not create an
  unwanted sequence for the single settings row.
- `BookingStatus` is an `enum.StrEnum` (Python 3.11+), so the members can be compared to plain
  strings and rendered directly in JSON.
- The compose `db` service publishes **5433** on the host because a native PostgreSQL 18 service
  already occupies port 5432 on this machine. Inside the compose network the port stays 5432.
- The booking model uses `MutableList.as_mutable(JSON)` for the `includes` list so in-place edits
  are detected by SQLAlchemy's unit of work.
- `alembic/env.py` keeps `from app import models as _models` as a side-effect import so every table
  is registered on `Base.metadata` before autogenerate runs.
- The availability response is **clamped to the booking window**: a request such as `days=31` never
  returns days that cannot be booked, and `start` outside the window is rejected with 422
  `date_out_of_range` (the same code the booking endpoint uses).
- `days` is validated by FastAPI (`1 ≤ days ≤ 31`); violations return 422 `validation_error`.
- The services module lives in `app/services/catalog.py` (the specification only named
  `availability.py`, `bookings.py` and `sms.py`); the public catalog query does not belong to the
  availability logic.
- The service layer returns frozen dataclasses; the routers convert them into Pydantic schemas, so
  ORM objects are never returned directly.
- In `app/schemas/availability.py` the `date` type is imported as `Date` because a Pydantic field
  named `date` would otherwise shadow the `datetime.date` annotation inside the class body.
- The phone number is normalized **first** in `create_booking()` (it is a request format check);
  the business rules then run in the order given by the specification. The normalized number is
  what gets stored, so `۰۹۱۲…`, `+98912…`, `0098912…` and `0912…` all end up as `09121234567`.
- A phone number without any prefix (`9121234567`) is accepted and normalized to `09121234567`;
  a false accept is harmless here, while a false reject would lose a customer.
- `GET /bookings/{code}` and `POST /bookings/{code}/cancel` answer with 404 `booking_not_found`
  for every mismatch — including a malformed phone number — so the API never reveals whether a
  code exists. Only the creation endpoint reports 422 `invalid_phone`.
- The rate limiter counts **every** attempt on `POST /bookings` (also the failed ones) to make
  brute force pointless; the counter is reset between tests.
- The booking code is generated with `secrets.choice(string.digits)`; a collision on
  `uq_bookings_code` is retried up to five times, a collision on `uq_bookings_active_slot` becomes
  409 `slot_taken`.
- The SMS is sent through `BackgroundTasks` and a provider failure is caught and logged, so it can
  never break the request.
- The SMS contains the **Gregorian** date (the same value the API returns). The frontend converts
  it to the Jalali calendar for display.
- `configure_logging()` switches `sys.stderr` to UTF-8 so the Persian log lines stay readable on
  Windows and inside the container.
- The admin password is hashed with bcrypt **once per process** (`lru_cache`) because bcrypt is
  intentionally slow; the plain text password never leaves the settings object.
- The admin token is a plain PyJWT (`HS256`) with `sub` = the admin username. `get_current_admin`
  rejects a token whose subject is not the configured admin.
- The login answers 401 `invalid_credentials` for an unknown user **and** a wrong password, so the
  API never tells which one was wrong.
- `PUT /admin/settings` behaves like a partial update: missing fields keep their current value
  (a full replace would silently reset the other settings).
- Field level setting errors (e.g. `open_hour: 30` or a weekday of 9) are Pydantic errors →
  422 `validation_error`; the cross field rule (`open_hour < close_hour`) is checked in the service
  → 422 `invalid_settings`.
- The status transitions are strictly `pending → confirmed|cancelled|no_show` and
  `confirmed → completed|cancelled|no_show`. Every other transition (including setting the same
  status again) is rejected with 409 `invalid_status_transition`.
- The slug of a service is immutable: `ServiceUpdate` forbids extra fields, so a PATCH that
  contains a slug is rejected with 422 `validation_error`.
- `DELETE /admin/closed-dates/{id}` answers 204 without a body.
- The dashboard counts `today_bookings` (today, cancelled excluded), `upcoming_bookings` (future
  days, pending/confirmed) and the revenue of the completed bookings of the current month.
- The PostgreSQL engine uses `connect_timeout=10` so a missing database produces a clear error
  instead of an endless wait.
- The request id middleware is a **pure ASGI** middleware (not `BaseHTTPMiddleware`), so the
  background tasks (the SMS) keep working exactly as before.
- The request log contains the path but never the query string, and the uvicorn access log is
  disabled in the container. The `SensitiveDataFilter` is a second safety net for the access log of
  a local `uvicorn` run.
- The published host port of the API is configurable with `API_PORT` because Windows reserves the
  port range 7912–8011 on some machines (8000 was blocked on the development machine, the local
  `.env` therefore uses `API_PORT=8080`). Inside the container the API always listens on 8000.
- The compose database publishes the host port **5433** for the same reason (a native PostgreSQL 18
  service owns 5432 on the development machine).
- The whole stack is configured by the `.env` of the **repository root**; `backend/.env` overrides
  single values for a local run and wins (pydantic-settings applies the env files in order, the
  last one wins). The root file keeps the container URL (`db:5432`), the local file the host URL
  (`localhost:5433`).
- The frontend is served by the vite dev server inside the compose stack and proxies `/api` to the
  api service, so the production setup needs no CORS at all (only a vite dev server on another
  port would).

## How to run

```bash
cd backend
.venv/Scripts/activate            # Windows
pip install -r requirements-dev.txt
pytest -q
ruff check .
```

Local API (PostgreSQL from compose):

```bash
cd ..                             # the repository root
docker compose up -d db            # PostgreSQL 16 on localhost:5433
cd backend
alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

Docker (the whole stack, from the repository root):

```bash
cp .env.example .env               # set SECRET_KEY and ADMIN_PASSWORD
docker compose up --build          # app on http://localhost:8081, api on 127.0.0.1:8080
```
